# 子專案 F：遊戲化（角色、XP、連續天數、7→14→30 天挑戰、斷掉的情勒信）

日期：2026-09-16
狀態：**設計定案**（兩個假設已於 2026-09-16 確認，見最後一節）；F1 待實作

參考對象是 App Store 的「Life Reset: 66 Day Habit」。它的機制拆開來是：每日任務給 XP、XP 升等級、連續紀錄的火焰、66 天挑戰、困難模式的懲罰、勵志卡收集、排行榜與好友、一堆附加工具。**只搬前四個**，理由記在〈不搬的東西〉。

## 使用者的決定

| 問題 | 決定 |
|---|---|
| 「一天有做」怎麼算 | **那一天安排的事情全部做完** |
| 要不要角色／頭像 | **要** |
| 免費版與 Pro 有沒有差 | **沒差**（遊戲化是留人的，不是收錢的） |
| 連續斷掉之後 | **跳出「情勒」的通知**：手機推播或郵件 |
| 挑戰的形狀 | **先 7 天，再 14 天，最後 30 天**（不是 66 天） |

## 一、一條原則：所有數字都是算出來的，不是存起來的

XP、等級、連續天數、挑戰進度、徽章——**全部從既有資料即時算出來**，跟 occurrence 引擎一樣（「循環項目的每一次發生從不被儲存，而是每次 render 時即時算出來的」）。

理由有三個，每一個都是踩過的坑：

1. **存一份帳本就要合併帳本。** 兩台裝置各自賺了 XP，三方合併會把 `game` 物件判成「兩邊都改過」跳對話框，除非另外寫一套「XP 相加、徽章聯集」的合併規則——那是 `threeWayMerge` 的第二套語意，有測試在守的東西不該為了一個數字長出分支。
2. **帳本會跟資料脫節。** 使用者刪掉一個項目、改掉一個日期，帳本上的 XP 還在；反過來從備份還原，帳本回到舊的。算出來的數字永遠跟畫面上的資料一致。
3. **存檔格式不必升版。** `STORAGE_VERSION` 不動，舊裝置開新存檔照樣能讀。

唯一新增的儲存是**完成的時間戳**（下一節），因為「有沒有按時做完」這件事沒有時間戳就算不出來。

## 二、唯一的新資料：`item.doneAt`

「那一天安排的事情全部做完」有一個隱含條件：**在那一天結束之前**做完。週一到期、週三才勾，週一不算完美的一天——否則連續天數就變成「有沒有補勾」而不是「有沒有按時做」。

現在只存「做完了」（`item.done` / `doneMap[occKey]`），不存「什麼時候做完」。所以加一個與 `doneMap` 同形狀的 map：

```js
item.doneAt = { [occKey]: <ms> }   // 單次項目用 'single'
```

- `setOccurrenceDone(occ, true)` 寫入 `Date.now()`；`false` 刪掉那個 key。**只在這一個函式寫**，它本來就是完成狀態唯一的寫入點。
- `snapshot()` / `applySnapshot()` / `normalizeItems()`（缺就補 `{}`、非數字的值丟掉）/ `threeWayMerge()`（走 `doneMap` 那條 map 合併）/ `seed()` 都要跟著改——同〈資料模型的收尾〉那份清單，漏一個就是靜默遺失。
- **改頻率清空紀錄時一併清空**（`btnConfirmItem` 那段清 `done`／`doneMap`／`overrides`／`skipped` 的地方），否則會留下孤兒 key。
- 富文字、ICS、分享的白名單合併（`mergeSharedEdit`）：被分享者勾選時伺服器只合併完成狀態，`doneAt` **也要一起帶**，否則別人幫你勾的那一次永遠「沒有時間」，那一天就永遠不完美。

**功能上線之前的完成紀錄沒有時間戳**，一律視為「不算」：連續天數從上線那天開始數（`GAME_EPOCH`，寫死一個日期常數）。角色從蛋開始，不追溯。追溯的話所有舊的完成都沒有時間、全部判成沒按時，會把上線第一天畫成「你以前什麼都沒按時做」。

## 三、引擎（純函式，零 DOM，可測）

一個新的區段 `// ================= 遊戲化 =================`，位置與 occurrence 引擎一樣在 IIFE 內、只依賴 `getAllOccurrences` 與日期工具。`tests/game.test.mjs` 從 `index.html` 抽這一段求值，同 `tests/occurrence.test.mjs`。

```
dayVerdict(dateStr, occs)   → 'perfect' | 'missed' | 'empty'
   perfect：那天有安排、每一次都在那天 23:59:59（本地時間）之前 doneAt
   missed ：那天有安排、至少一次沒有或太晚
   empty  ：那天沒有安排（略過的不算安排；「不在」不影響——不在就是不在，見假設 A）

streakOf(todayStr, occsByDay) → { current, best, todayPerfect }
   從昨天往回數連續的 perfect，empty 跳過不斷也不加；今天若已 perfect 再 +1
   best 是歷史最長（給 30 天徽章用）

xpOf(...)  → 整數
   每一次按時完成 +10；每一個完美的一天 +30；每一個徽章第一次拿到 +100
   全部從 doneAt 與 verdict 算，不存

levelOf(xp) → { level, into, need }
   門檻遞增：第 n 級需要 100 × n × (n+1) / 2（1 級 100、2 級 300、3 級 600……）
   上限刻意不設；角色的外觀只到第 6 階（見〈角色〉），之後只長數字

challengeOf(streak) → { target: 7|14|30|null, done: n, unlocked: [...] }
   梯子固定 7 → 14 → 30：best ≥ 7 才解鎖 14，best ≥ 14 才解鎖 30，30 拿到之後 target 為 null
   當下的進度用 current 數（斷了就從 0 開始爬同一階，不掉階）

badgesOf(...) → [{ id, earnedOn }]
   'first'（第一次按時完成）、'ten'、'fifty'、'hundred'（按時完成的次數）
   'streak7'、'streak14'、'streak30'（挑戰三階）
   'perfectWeek'（週一到週五都 perfect，empty 不算破）
```

**「今天」永遠以本地日期判斷**（`ymd(new Date())`），與整個 app 一致；伺服器端（第五節的 cron）用 UTC+8，跟 AI 與提醒信一樣。

## 四、畫面

### 角色

一株植物，六階：種子 → 發芽 → 小苗 → 小樹 → 開花 → 結果。理由：

- **與「紙與光」一致**：苔綠與暖沙本來就是底圖的顏色，不必為它另闢一套視覺語言。
- **不用任何外部圖檔**：六階都是 inline SVG（幾何形狀＋一點曲線），同空狀態的插畫 `emptyArt()`；「單檔不引外部資源」的前提不變。
- **等級 → 階段**：1–2 種子、3–4 發芽、5–7 小苗、8–11 小樹、12–16 開花、17+ 結果。連續 3 天以上葉子上有一點光；連續斷掉那天植物**微微垂下**，不枯、不死——那是情勒信的工作，不是畫面的（畫面上已經有逾期的紅字在嚴肅了）。

### 放在哪裡

| 位置 | 內容 | 為什麼 |
|---|---|---|
| header 招呼語旁邊 | 小小的角色＋「Lv.7」＋連續天數（有火焰 emoji 🔥 但只在 ≥ 2 天時出現） | 每次打開都看得到，但不佔版面 |
| 「我的帳號」新增一區「🌱 我的角色」 | 大的角色、XP 條、連續／最長、目前挑戰的進度條（7 格／14 格／30 格）、徽章牆 | 要停下來看的東西放這裡，同其他帳號設定 |
| 勾掉今天最後一件時 | toast：「今天全部做完了。+30 XP，連續 N 天。」 | 那一刻才是遊戲化真正發生的地方 |
| 週一回顧 | 現有那一句長成一張卡：上週做完幾件、完美幾天、賺了多少 XP、有沒有新徽章 | 已經有位置、已經有測試（N=0 不出現那條不變） |
| 升級 | 角色旁邊冒一下光（同打勾的 `.pop`，`animationend` 拿掉；`prefers-reduced-motion` 一律關） | 輕。這是紙與光，不是霓虹燈 |

**紅線不動**：逾期的紅字、字重、顏色一個都不改；遊戲化只加東西不減東西。`tools/check-deps.mjs` 那兩條斷言照樣守著。

### 不改日期救火焰

「保連續」會讓人想把今天做不完的東西**往後改一天**——畫面看起來完全正常，只是那個日期默默地不對了（〈前置作業不自動順延〉那節防的正是這件事）。

要擋它就得知道「這個日期是什麼時候被改的」：覆寫（`overrides`）現在只存新日期、不存改動時間，防它等於第二份時間戳，加上一堆邊界（改早算不算、循環規則整個改掉算不算）。

取捨：**v1 不防**。同一個人在同一份工具裡騙自己，工具能擋的本來就有限；先寫下來，看實際有沒有人這樣做再說。

## 五、斷掉之後的情勒信

**只有 email 走得通。** 手機推播是子專案 B（還沒做），做好之後這一封改成推播＋郵件二選一或都要；v1 是郵件。

走現有的每日 cron（08:00 台北）與 `reminder_feed`：

- 前端的 `buildReminderDigest()` 每一筆多帶 `a: doneAt`（沒有就不帶），另外整份 digest 多一個 `streak: { current, best }`——**由前端算好推上來**，理由同 ICS 與提醒信：引擎只存在前端單檔內，Worker 不重算一份。
- cron 多一步 `sendStreakBroken`（獨立 try/catch，同其他三步）：昨天有安排、且不是每一件都在昨天結束前完成、且推上來的 `streak.current`（推送當時）≥ 2 → 寄一封。**只寄那一天一次**（`streak_mail_ymd`），連續是 0 或 1 的人不寄——「沒事就閉嘴」那條在這裡更重要：每天一封「你昨天又沒做完」只會訓練人忽略這個寄件人。
- **以最後一次同步為準**：使用者昨天 23:50 勾完但沒同步，今天早上會收到一封冤枉的信。與提醒信的取捨相同，可接受；`flushPendingWrites()` 讓這種情況很少發生。
- 帳號頁的提醒區多一個開關「連續斷掉時寄信給我」，預設開（同提醒信預設開的理由）；`reminder_feed` 多一欄 `streak_mail`（migration 007）。
- 記進 `cron_runs`，`/admin` 的排程狀態多一列。

### 語氣：撒嬌，由角色開口

使用者的裁決：**會撒嬌的口氣**。所以這封信不是系統在講話，是**那株植物**在講話——它有立場撒嬌（火焰是它的、葉子是它的），系統沒有。

> 主旨：欸……昨天你沒有來
>
> 我們一起走了 12 天耶。
> 昨天你沒有把事情做完，我的火焰熄掉了，葉子也垂下來一點點。
> 我不生氣啦，只是有點想你。
> 今天可以回來嗎？把〈標案初審〉和〈查廠報告〉做完，我就會再亮起來。
>
> ——你的小植物

三條規則：

- **講事實**（幾天、哪幾件），**不評價**（沒有「你放棄了」「你又……」）。撒嬌的力量來自「它在等你」，不是來自羞辱。
- **第一人稱是植物**，署名也是。同一個角色在畫面上會垂下葉子，在信裡會說想你——是同一件事的兩面。
- **不寫「加油」、不寫「沒關係」**：前者是提醒信的語氣，後者會把這封信的用途取消掉。

罵人的信會被封鎖寄件人，然後逾期提醒也一起收不到；撒嬌的信不會。

## 八、不搬的東西（刻意）

| Life Reset 有 | 不搬的理由 |
|---|---|
| 困難模式的懲罰（扣 XP、扣等級） | 逾期本身就是後果，紅字已經在講了。扣血會把注意力從工作移到遊戲 |
| 排行榜、好友挑戰 | 我們的分享是「一起看同一份排程」，不是比賽；多人社交是另一個產品 |
| 勵志卡收集 | 要一直產內容；每日記錄的提示語已經在做「輕輕說一句」 |
| 番茄鐘、冥想、卡路里、書摘 | 跟排程無關；那個 app 評論裡罵最兇的就是這些被鎖在牆後面 |
| 66 天 | 使用者選了 7→14→30 |
| 遊戲化放在 Pro 後面 | 使用者的裁決：沒差 |
