# AI 小幫手側邊欄（DeepSeek）

日期：2026-09-08
狀態：**設計完成，尚未實作**

## 一句話

右側一條側邊欄，可以問排程、要摘要，以及**把「這段時間要做哪些專案」拆成可勾選的小項目清單**——AI 只負責提案，按下「加入」的是人。

---

## 一、為什麼不能用本機的 Ollama

原本的構想是「Ollama 的 API key ＋ DeepSeek 的模型」。那是兩個東西混在一起了：

| | 跑在哪 | 要金鑰 | Worker 連得到 |
|---|---|---|---|
| Ollama **本機** | 你的電腦 `localhost:11434` | 否（本來就沒有） | **否** |
| Ollama **雲端** | `ollama.com/api` | 是（`Bearer`） | 是 |
| **DeepSeek 官方** | `api.deepseek.com` | 是 | 是 |

本機版有兩層各自獨立的阻擋，兩層都得繞過才行得通：

1. **Worker 跑在 Cloudflare 的機器上，看不到你家的 localhost。** 這不是設定問題，是網路拓撲。
2. **就算改成讓瀏覽器直接連**——Chrome 142 起完整實施 Local Network Access，HTTPS 頁面連本機服務預設被擋，會跳權限詢問，而且 Ollama 那端還要自己送 `Access-Control-Allow-Private-Network: true` 與 CORS 標頭。

所以走雲端 API。**已選定 DeepSeek 官方**：一把金鑰、OpenAI 相容格式（日後想換別家只要改 base URL），而且便宜。

---

## 二、金鑰只能放在 Worker

`public/index.html` 是任何人都下載得到的檔案。金鑰放進去等於公開它。

```
瀏覽器  ──►  /api/ai  ──►  api.deepseek.com
             （Worker，持有 DEEPSEEK_API_KEY）
```

與 `AGENTMAIL_API_KEY` 完全相同的模式：Worker secret，不進 repo、不進備份、不回傳給前端。

**單機模式（雙擊開檔）偵測不到 `/api/ai` 就不顯示側邊欄。** 這是 `cloudPull()` 的 `absent` 分支，不是 `failed`——使用者不該看到一個他永遠用不了的入口。

---

## 三、會花錢，所以有兩條硬性要求

DeepSeek V4-Flash 約每百萬輸入字 US$0.14。實際使用者的整份排程約 19KB，「摘要這個月」單次成本約**新台幣三毛**。很便宜，**但不是零**，而且按鈕連點 100 下就是 100 次。

### 1. 一定要限流

沿用 `src/throttle.js` 既有的滑動窗口，維度換成 `user_id`：

- 每分鐘 5 次、每天 50 次（初版數字，之後看實際用量調）
- 超過**回 429 並說明還要等多久**，不要靜默失敗——〈降級可以，沉默不行〉

### 2. 花費一定要看得見

每次呼叫把 token 數記進 `ai_activity`，`/admin` 顯示本月累計。

理由與〈看得見的備份才是備份〉完全相同：**看不見的花費會失控**，而 Cloudflare 與 DeepSeek 的後台都不是有人會每天去翻的地方。這一條不是附加功能，是這個功能能不能安心放著的前提。

### 3. 只送需要的那一段

問「這週有什麼」不必把整年的排程送出去。送出前先用既有的 `currentRange()` 裁切。省錢是次要的，**減少外送的資料量才是主要的**。

---

## 四、資料會送到第三方，這件事要說

實際使用者的排程包含「管制藥品申報」「管制藥品歸檔」「PVF 藥品追溯申報」這類**藥品法規遵循**的工作內容。用雲端 AI 表示那些文字會離開這個系統。

- 側邊欄**第一次開啟時顯示一次明確說明**，不是藏在設定裡的小字。
- 這不是「不能做」，是**當事人應該知道再決定**。這個判斷不該由開發者單方面代下。

---

## 五、能做什麼：沿用 WebMCP 那份文件的判準

`2026-08-27-webmcp-design.md` 已經決定過同一組問題，那些決定在這裡**一字不改**適用：

| 可以 | 不可以 |
|---|---|
| 查排程、查逾期、查專案 | **刪除** |
| 新增項目 | **改日期** |
| 標記完成／未完成 | **改名稱** |
| 給整理建議（只建議，不動手） | |

理由不是「危險」而是**發現得了發現不了**：多一個項目看得到，少一個項目看不到，而日期改錯一天**永遠不會被發現**——畫面完全正常，只是那個日期默默地不對了。

同樣沿用的還有兩個介面契約：

- **查詢的回應必須帶出 `itemId` 與 `occKey`**，「標記完成」才有東西可以指。occurrence 從不被儲存，AI 拼不出 occKey。
- **日期一律絕對的 `YYYY-MM-DD`**，而且每個查詢的回應都附上 `today` 當錨點。語言模型換算相對日期容易差一天，而差一天在排程系統裡就是錯的。

## 六、核心功能：工作分解（提案 → 勾選 → 才寫入）

這是使用者自己提出的流程，而它**比原本的設計更安全**：

> 原本：AI 直接寫 → 寫錯了按復原（**事後補救**）
> 現在：AI 提案 → 使用者勾選 → 才寫入（**事前確認**）

最壞的情況從「資料被改錯、等人發現」變成「畫面上多了一份沒被採納的清單」。這個差別大到值得讓它成為**所有寫入的預設形狀**，而不只是這一個功能的作法。

### 流程

1. 使用者輸入：「10 月要做中秋特賣專案跟醫護優惠購」＋期間
2. 前端把**既有的標籤、大項目清單、以及幾個既有項目的命名風格**一起當上下文送出——讓拆出來的東西跟她原本的寫法一致，而不是 AI 自己的風格
3. AI 回一份結構化提案（見下）
4. 側邊欄畫成**可勾選清單**，預設全勾，每一項的標題與日期都可以就地改
5. 按「加入」→ **只有勾起來的**走 `commit()` 寫進去

### 提案的形狀

```json
{
  "groups": [{
    "title": "中秋特賣專案",
    "suggestedTag": "特賣",
    "items": [
      { "title": "確認特賣品項與售價", "type": "work", "date": "2026-10-03",
        "subtasks": ["跟採購確認庫存", "產出價格表"] }
    ]
  }]
}
```

拆出來的步驟直接落進今天做好的 `item.subtasks`——**不需要為這個功能發明新的資料結構**。

### 三個不能拿掉的判斷

- **AI 永遠不直接寫。** 它只回提案；寫入發生在使用者按下按鈕那一刻，走既有的 `commit()`。
- **用結構化輸出，不要叫模型「回 JSON」再自己 parse。** DeepSeek 是 OpenAI 相容，用 `response_format: {"type":"json_object"}`。即便如此仍要驗證——外部輸入永遠要在自己這一側再驗一次。
- **日期驗證失敗的那一項標紅並預設不勾，而不是丟掉。** 丟掉的話使用者不會知道 AI 本來想排在哪天；標紅則讓她看得到、也改得動。

### 一個要問清楚的地方

「加入一個**專案**的項目內」——這個系統裡有兩套互不相干的「專案」：

| | 是什麼 |
|---|---|
| `majorProjects`（大項目） | 純分類標籤，小項目用 `parentId` 歸屬它 |
| `ganttProjects`（專案頁） | 完全獨立的另一套資料，各自帶 `tasks[]` 與 `notes` |

初版**兩個都支援**，在「加入」那一步讓使用者選目標。這比猜錯再改便宜，也省掉一次來回。

---

## 七、記錄與復原

- 每一次寫入仍然走 `deleteWithUndo()` 的通用形狀（拍快照 → `commit` → 6 秒復原 toast）。有了勾選這道關卡，它的角色從「主要防線」降為「第二層」，但不該拿掉。
- `ai_activity` 表（同 `admin_activity` 的模式，保留 90 天，寫入失敗只 `console.warn`）記下：問了什麼類型的操作、寫進去幾項、用掉多少 token。
- **單機模式留不了永久記錄**（沒有後端）。要在畫面上寫明，而不是顯示一個永遠空白的清單。

---

## 八、測試

**絕對不在測試裡打真的 API。** 要錢、回應會變、CI 也沒有金鑰。用一個假的 `fetch` 注入，驗的是**我們這一側的行為**：

| 驗什麼 | 怎麼驗 |
|---|---|
| 提示詞有帶上 `today` 與裁切過的區間 | 檢查送出的 body |
| 回應是壞掉的 JSON 時不會弄壞整個 UI | 餵一段壞字串 |
| 日期不合法的項目會標紅且預設不勾 | 餵一個 `2026-13-45` |
| **沒勾的項目絕對不會被寫進去** | 取消勾選後按加入，比對 `items` |
| 超過限流回 429 且訊息說得出還要等多久 | 直接打 handler |
| 金鑰不會出現在任何回傳給前端的東西裡 | 掃回應字串 |

最後一條要像備份那個測試一樣，是**明確的絆線**。

**測不到、要誠實說的**：AI 拆出來的東西好不好用，測不到。假的回應驗的是我們的處理，不是模型的品質。所以上線後第一件事是拿她真實的專案名稱實際跑幾次，看拆出來的東西她願不願意勾。

## 九、分階段

| 階段 | 內容 | 為什麼這個順序 |
|---|---|---|
| **一** | Worker proxy、金鑰、限流、`ai_activity`、成本顯示、**唯讀問答與摘要** | AI 改不了任何東西，可以放心在真實資料上試，順便驗證它看不看得懂這份排程 |
| **二** | **工作分解**（提案 → 勾選 → 加入） | 使用者最想要的那一個。有勾選這道關卡，風險比階段三低 |
| **三** | 新增／標記完成／整理建議 | 走既有工具，形狀與階段二相同 |

階段一沒有任何寫入路徑，**先合併也完全沒有副作用**。

## 十、還沒決定的事
