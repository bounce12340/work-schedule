## A：大標題換微軟正黑體

```css
--sans-heading: 'Microsoft JhengHei', '微軟正黑體', 'PingFang TC', 'Noto Sans TC', var(--sans);
```

套用在兩個地方，都是「工作排程確認系統」那一行：`.brand-title`（header）與 `.app-auth-title`（app 登入畫面，有兩處 markup）。

**為什麼是一個新的 CSS 變數而不是就地寫死**：顏色那一條規則（「新增顏色一律加進 `:root` 與 `[data-theme="dark"]` 兩組變數，不要在個別選擇器裡硬寫色碼」）背後的道理對字體同樣成立——三處寫死，日後改字體就會漏掉一處，而漏掉的那一處**看起來只是「有點不一樣」**，不會有任何檢查紅。

**它取代的是 `--serif`，不是加在它旁邊。** 〈這個介面有兩種聲音〉那一節把宋體指派給「人在說話」，而系統標題是其中一項。這次的改動把**系統標題**這一項從「人的聲音」移到「產品的招牌」——招呼語、空白時刻、每日記錄、做完之後那一句仍然是宋體。兩種聲音的規則本身沒有變，只是標題換邊站。

離線時 Google Fonts 拿不到，微軟正黑與蘋方都是**系統內建**，所以這一行在離線時反而比原本的宋體更穩。

## C：不在與休假

### C-1 兩種狀態的定義

| | 不在（away） | 休假（leave） |
|---|---|---|
| 意思 | 人不在辦公室，**但仍在上班** | **正式請假** |
| 例子 | 出差、開會、場勘 | 特休、病假、事假 |
| 時段 | 幾點到幾點 | 幾點到幾點 |
| 圖示 | 固定 🌴 | **每一次自己挑一個 emoji** |
| 日曆長相 | 斜線紋 ＋ 右上角 🌴 | **整格一層淡色玻璃 ＋ 中間一個大圖示** |
| 逾期 | 不影響 | 不影響 |
| 提醒信／推播 | 照寄照推 | **那一天完全不寄不推** |
| 行事曆訂閱 | 不進去 | 不進去 |

### C-2 資料模型（使用者選的「做法二」）

頂層的 `awayDates: Set<ymd>` 換成單一的 `absences`：

```js
absences = {
  '2026-09-15': [
    { kind:'away',  from:'09:00', to:'12:00' },
    { kind:'leave', from:'13:00', to:'18:00', icon:'🏖️' }
  ]
}
```

- `kind` 只有 `'away'` 與 `'leave'` 兩個值，其餘一律丟掉（白名單，同富文字過濾器的第一原則）。
- `from` / `to` 是 `HH:MM`，**兩者皆可為 null＝整天**。整天是最常見的情況，不該逼使用者每次都填時間。
- `icon` 只有 `kind==='leave'` 才有；**單一 emoji 字元**，不是圖檔——`<img src>` 會破壞「單檔、零外部相依」的前提（同〈氛圍層的三個實作決定〉的第二條）。
- 陣列**排序後儲存**（依 `kind`、再依 `from`），理由同 `normalizeTags` 與 `normalizeDependsOn`：三方合併以 stableStringify 比對，順序不同會被誤判成「兩邊都改過」。

**為什麼選一個清單而不是兩個**：使用者選了「同一天可以兩種並存」，而兩個清單就得在兩邊之間互相對照時段，那份對照邏輯寫兩份遲早會走鐘——這是這份 CLAUDE.md 反覆出現的失敗模式（「只要兩邊必須一致，就要有東西去比」）。一個清單讓並存天生成立。

**刻意不檢查時段重疊。** 「9:00-12:00 出差」與「10:00-18:00 休假」在資料上互相打架，但系統不當裁判：真實世界就是這麼模糊（上午的會開到一半提早請假），而系統一旦判定「這不合法」就得決定砍掉哪一邊，那是在使用者沒看的時候改掉他填的東西。

### C-3 舊資料怎麼搬

`applySnapshot()` 同時認得兩種形狀：

```
s.absences 是物件        → 直接用（正規化後）
s.awayDates 是字串陣列   → 每一筆變成 { kind:'away', from:null, to:null }
兩個都沒有               → 空物件
```

**舊鍵不寫回去。** `snapshot()` 只輸出 `absences`；`awayDates` 只在讀取時被認得。兩邊都寫的話，「哪一個才是真的」會在某一次同步之後變成猜謎。

**這會讓舊版頁面讀不到新資料**，而那正是 `STORAGE_VERSION` 與 `migrateSnapshot()` 存在的理由：舊 build 拒絕套用、把原始內容搬到 `workSchedule.v1.unreadable` 再降級，而不是靜靜地把使用者的休假全部弄不見（見〈儲存層的三個設計約束〉第 4 點）。所以 `STORAGE_VERSION` 要加一。

### C-4 三方合併

`tmMergeSets` 比的是「這個字串在不在集合裡」，裝不下物件。新增 `tmMergeAbsences(base, local, remote)`：

- **以日期為單位**比對，值用 stableStringify 比。
- 只有一邊改過 → 採用那一邊。
- 兩邊都改過同一天 → **整天視為衝突**，走既有的衝突對話框。
- 一邊刪掉整天、另一邊沒動 → 刪除生效。

**粒度刻意停在「一天」而不是「一筆時段」。** 時段層級的合併要回答「這兩筆是同一筆被改過，還是各自新增的兩筆」，而那需要每一筆各自的 id——為了一年用不到幾次的欄位背一套身分系統不划算。一天當成一個不可分割的單位，語意也比較好解釋：「這一天你們兩邊填的不一樣，選一個」。

### C-5 「休假那幾天閉嘴」的實作

**判斷在前端，不在 Worker**——與 `ot`、`streak_current`、ICS、逾期提醒信完全相同的模式，理由也相同：occurrence 引擎與日期語意只存在 `public/index.html` 裡，Worker 重寫一份必然分歧，而**提醒寄錯比沒有提醒更糟**。

`buildReminderDigest()` 多帶一個 `leaveDays: ['2026-09-15', ...]`（只列**有 leave 的日子**，不列 away）。Cron 的 `sendOverdueReminders` 與推播那一步在寄之前先問：今天在不在 `leaveDays` 裡？在 → 這一天整封不寄、整則不推。

**「閉嘴」是整天跳過，不是把那幾項挑掉。** 挑掉會產生一封說「你有 3 件事」但實際上漏講 2 件的信——那比不寄更糟，因為收件人會以為那就是全部。

**跳過的那一天不寫 `last_sent_ymd`。** 同「寄失敗刻意不寫」：沒寄成功就不算寄過。休假結束後的第一天要能補上（逾期項目本來就會繼續累積，不會消失）。

**`leaveDays` 只影響「主動送出去的東西」。** 畫面上的紅字、指標卡、連續天數、行事曆訂閱**一個都不動**。

### C-6 畫面

**🌴 從左上角移到右上角**（使用者第 5 項）。右上角因此有兩個小記號：由右往左是 ✎、🌴。`.cal-away-mark` 的 `left:6px` 改成 `right:22px`。

**休假整格換底色，用一層偽元素，不是 `background-color`。**

程式碼裡原本寫著一條規則，而使用者的選擇與它相牴觸，所以要把新的理由寫下來：

> 用斜線紋而不是換底色：底色已經被「今天」與「已選取」用掉兩層了，再加一層三者疊起來會分不出誰是誰。

這條仍然成立——所以休假**不搶 `background-color` 那一格**，改用 `.cal-cell.leave::before` 疊一層低 alpha 的色片：

```
內容文字
  ↑
中間的大圖示（極低 opacity，pointer-events:none）
  ↑
.cal-cell.leave::before  ← 「整格換底色」在這一層
  ↑
background-color：今天的琥珀 / 已選取的灰
background-image：不在的斜線
```

「今天剛好休假」因此仍然看得出來是今天（`.cal-daynum` 的琥珀色照舊保留，同既有的 `.cal-cell.today.away` 那一行）。

**中間的圖示是浮水印，不是主角。** 它的 opacity 必須低到不影響上面的文字——`tools/check-contrast.mjs` 要新增一個 pass：把畫面逼成「有休假的那一格」，量格子裡的項目文字。這一條不能省，理由寫在〈「畫面上沒有這個元素，略過」是一條永遠不會執行的斷言〉：要按幾下才看得到的東西，也要量。

**設定入口只有一個**：日曆詳情區那一排按鈕，單日與拖曳選出的區間都適用（沿用「不在」的既有規則——同一份狀態兩個入口遲早不同步）。按下去展開一個小面板：選 away／leave、填幾點到幾點（可留空＝整天）、leave 再挑一個 emoji。

**列上的附註**：不在維持 `🌴 不在`，休假多一個同形狀的 `<選的emoji> 休假`。兩者都**與逾期的紅字並存**——`tools/check-deps.mjs` 已經有一條斷言守著「逾期標記與 🌴 必須同時出現在同一列」，休假要加上同樣的一條。

### C-7 要同步改的地方（漏一個就是靜默的資料遺失）

`snapshot()` / `applySnapshot()` / `normalizeAbsences()`（新） / `threeWayMerge()`（`tmMergeAbsences`） / `clearLocalData()` / `seed()` / `buildReminderDigest()`。

## B：純告知的項目

### B-1 它是一個開關，不是第四種類型

`item.noticeOnly`（布林，預設 false）。

**不做成第四種 `type`**，因為 `type` 已經承載了顏色與分類（work／meeting／assignment），而「純告知」與「這是工作還是會議」是**兩個互相垂直的問題**——一場只是要知道、不必準備的會議，兩邊都要表達得出來。

做成開關還有一個免費的好處：跨多天的事項（`item.endDate`）自動就有了，不必為使用者的第 3 項另外寫一條路徑。

### B-2 「不算進去」的完整清單

使用者的裁決是「純告知就不要算進去」。「算進去」在這份程式碼裡有 8 個地方，**全部都不算**：

| 地方 | 純告知 |
|---|---|
| 今日待辦卡 / 本週待辦卡（`renderMetrics`） | 不進去 |
| 逾期卡與列上的紅字 | **永遠不逾期** |
| 今日會議卡 | 不進去 |
| 勾選框 | **不長勾選框** |
| 「只看未完成」篩選 | 不受影響，一直都在 |
| 已完成區 | 永遠不進去 |
| 遊戲化（`dayVerdict` / 連續 / XP / 角色） | 不算。那天只有純告知＝`empty` |
| 專案進度百分比 | 不算分母 |

實作上收斂成一個述詞 `isActionable(occ)`，上面八處全部問它——**不要在八個地方各寫一次 `!o.item.noticeOnly`**，那正是〈勾選不重建看板〉警告的「在增量路徑複製一份遲早會走鐘」的形狀，而走鐘的症狀是「畫面看起來是對的，只是數字不對」。

### B-3 通知

| 管道 | 有沒有純告知 |
|---|---|
| 逾期提醒信 | ❌ |
| 推播 | ❌ |
| 行事曆訂閱（ICS） | ✅ |

**為什麼行事曆要、信與推播不要**：行事曆是「我自己去翻」，信與推播是「它跑來找我」。這與使用者在〈C-4〉選的是同一條線。

ICS 裡的純告知事件**不帶 VALARM**（不設提醒鬧鐘），它只是一格佔位。

### B-4 過期之後

留在看板上，加 `.notice-past`。

**淡化不能只靠把顏色調淡。** 〈「畫面上沒有這個元素，略過」是一條永遠不會執行的斷言〉那一節抓到過兩個已經上線很久的案例，修法都是「階層改用字級表達，不要靠把顏色淡到讀不了」。所以這裡的做法是：

- 字級降一階（15px → 13px）
- 加一個 `已過` 的小標
- 顏色用 `--text-dim`，**且必須通過 4.5:1**（`tools/check-contrast.mjs` 要把這個狀態加進 `AFTER_CLICKS` 清單）

## D：櫻花樹

### D-1 它接手，植物退休

六階不變，換成四季循環：

| 階 | 名稱 |
|---|---|
| 0 | 新芽 |
| 1 | 抽枝 |
| 2 | 花苞 |
| 3 | 綻放 |
| 4 | 花落 |
| 5 | 新芽（新的一輪） |

第 5 階回到第 0 階的樣子但**樹幹更粗**——「不停的四季循環」要看得出來是第幾輪，否則等級 6 與等級 1 長得一模一樣，升級就沒有意義了。

`levelOf(xp)` 的門檻、`GAME_EPOCH`、挑戰梯子、徽章、`dayVerdict` 的語意**一個都不動**。這次只換畫皮：`plantSvg(stage)` 換成 `sakuraSvg(stage)`，顏色照舊走 CSS 變數（`:root` 與 `[data-theme="dark"]` 兩組都要）。

**連續斷掉那天仍然只是「微微垂下」**，不枯不死——那是信的工作（F2），不是畫面的。

### D-2 連鎖反應：信要跟著改口

`src/handlers/reminder.js` 的 `sendStreakBroken` 是**植物的第一人稱**，署名「——你的小植物」。植物退休之後那封信必須跟著改成櫻花樹的口吻與署名。

不改的症狀是：**畫面上是櫻花樹，信卻是別的植物寫的**。它不會壞、不會報錯，只會讓人覺得哪裡怪怪的——這正是這份文件裡反覆出現的那一類 bug。

要一起改的：信的文案與署名（中英兩版）、`tests/state.test.mjs` 裡比對信件內容的斷言、I18N 字典裡與植物有關的字串、帳號頁「我的角色」那一區的說明文字。

### D-3 載入畫面：它是遮罩，不是關卡

**絕對不能擋住第一次繪製。**

〈字型不阻擋首次繪製〉量過一組數字：CDN 慢 1.5 秒時，擋住繪製會讓 FCP 從 536ms 變成 2060ms。一個純粹為了好看而存在的動畫，沒有資格讓 app 開起來慢四倍。

所以：

1. 畫面照常繪製，**不等任何東西**。
2. 櫻花樹的動畫蓋在**上面**（`position:fixed`，最上層）。
3. 資料就緒（`renderAll()` 跑完一次）就淡出移除。
4. **有一個上限**（1200ms），到了就走，不管資料好了沒。同〈開機看門狗〉的道理：不問卡在哪，只問「到現在有沒有走到任何一種結局」。
5. `prefers-reduced-motion` 一律**完全不顯示**。它是純氛圍、沒有任何資訊在裡面，是最該被關掉的那一種動畫（同光暈的處理）。

**它只在開機出現一次**，不是每次切頁籤都播。切頁籤時播一次動畫，第三次就會變成「這個 app 好慢」。

**成長動畫的階段跟著使用者目前的等級**——開機播的是「從種子長到你現在這一階」，不是每次都從頭長到滿。那樣才有「我的樹」的意思。

### D-4 驗證

`tools/check-ambience.mjs` 要加：

- 載入畫面在 1200ms 內一定消失（**上限本身要被測到**，不是只測「正常情況會消失」）
- `prefers-reduced-motion` 開著時它根本不出現
- 升級的光仍然只在升級那一次（看計算後的 `animationName`，同既有那一條）

`tools/smoke.mjs` 的七輪都要確認載入畫面不會擋住既有的斷言——它蓋在最上層，`page.click()` 會打到它。

## 明確不做的事

| 不做 | 理由 |
