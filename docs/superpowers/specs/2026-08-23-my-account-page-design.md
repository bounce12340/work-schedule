# 「我的帳號」分頁設計

日期：2026-08-23

## 問題

帳號相關的功能散在三個地方，而且**最重要的設定放在最不容易被發現的位置**：

| 現在在哪 | 有什麼 |
|---|---|
| header 的 `.account-box` | email、帳號管理、變更密碼、登出 |
| header 的 icon 按鈕 | 語言、主題、提醒鈴 |
| **footer 的 `.backup-row`** | **匯出／匯入備份、行事曆訂閱、逾期提醒開關＋提前天數** |

逾期提醒與行事曆訂閱是需要「停下來設定」的東西，卻被放在整頁最底部的頁尾。實際結果可以量化：系統上線至今，`ics_feed` 是 **0 筆**（沒有人產生過訂閱連結），兩位使用者的提醒也一直是關的，直到 2026-08-23 手動打開。**沒有人找得到的功能等於不存在。**

## 目標

把「需要停下來設定」的東西收進一個看得見的地方，並在過程中不破壞任何既有行為。

**非目標**（刻意不做）：

- 不改任何一個既有功能的行為。這一批只搬位置、加說明。
- 不做 Google 日曆雙向連動（理由見附錄）。
- 不重寫控制項的事件綁定（理由見〈做法〉）。

## 形式：主畫面的第五個分頁

在「項目安排 / 日曆 / 專案 / 共享」旁邊加一個「我的帳號」。

考慮過但沒有採用的兩種：

| 形式 | 為什麼不採用 |
|---|---|
| 大型 modal | 內容夠多，塞進彈窗在手機上會很擠 |
| 獨立的 `account.html` | **會破壞單檔雙擊開啟的前提**——離線開 `index.html` 時連不到那一頁，而匯出備份、主題、語言這些離線也該能用的功能就進不去了 |

分頁**在單機模式下也存在**，只是雲端相關的區塊隱藏。整個分頁消失會讓使用者以為功能不見了。

## 做法：搬移既有元素，不重寫

既有的控制項都是用 `getElementById` 取得、在 JS 內綁 `.onclick`。因此**把 HTML 搬到新分頁的 markup 裡，事件綁定完全不必更動**——行為零風險。

搬完之後為每一項補上標題與說明文字（現在頁尾那排按鈕沒有任何說明）。

**刻意不做的第三種選項**：頁尾保留一份、分頁再放一份。同一個設定有兩個顯示位置，狀態遲早不同步，而那是最難查的一類 bug。

## 分頁內容

| 區塊 | 內容 | 來源 | 單機模式 |
|---|---|---|---|
| 👤 帳號 | email、角色、加入時間、「變更密碼」 | header | 隱藏 |
| 📧 逾期提醒 | 開關、提前天數、寄到哪個信箱 | footer | 隱藏 |
| 📅 行事曆訂閱 | 產生／重新產生連結、**怎麼用的說明** | footer | 隱藏 |
| 💻 登入中的裝置 | 裝置清單、登出其他裝置 | **新功能** | 隱藏 |
| 🎨 顯示偏好 | 主題、語言 | header（圖示按鈕**保留**） | 顯示 |
| 💾 備份 | 匯出、匯入 | footer | 顯示 |

**留在原地不搬的**：登出、帳號管理（管理者入口）、主題與語言的 icon 按鈕。這些都是「按一下就完成」的動作，收進分頁只會多一次點擊。顯示偏好在分頁裡是**第二個入口**，價值在於能寫一句「這是這台裝置的偏好，不會跟著帳號走」——那件事目前沒有任何地方說明。

單機模式下，隱藏的區塊位置顯示一行「這些功能需要登入帳號後才能使用」，而不是留白。

## 後端：只有「登入中的裝置」需要動

### 兩個既有程式碼要順帶調整的地方

自我審查時發現這份設計原本漏掉的前提，兩者都很小但少了就做不出來：

1. **前端目前拿不到「加入時間」。** `getSessionUser` 的 SELECT 沒有 `u.created_at`，`handleGetState` 回的 `me` 也只有 email／role／status。要在分頁顯示「2026-07-29 加入」，得把 `created_at` 一起帶出來。
2. **`createSession(env, userId)` 拿不到 request，取不到 user agent。** 簽名要改成接受一個 user agent 參數（由 `handleLogin` 從 `request.headers.get('user-agent')` 取得後傳入）。這是唯一會動到既有函式簽名的地方，呼叫端只有一處。

### schema

```sql
ALTER TABLE sessions ADD COLUMN user_agent   TEXT;
ALTER TABLE sessions ADD COLUMN last_seen_at INTEGER;
```

兩者都可為 NULL：升級前就存在的 session 沒有這些資料，顯示為「未知裝置」即可，不需要強迫他們重新登入。

依〈資料庫結構變更〉的規矩，這是**欄位**變更，因此要在 `migrations/` 留一支 SQL 並在部署前跑過。

### 記什麼、不記什麼

記 **user agent 與時間**，**不記 IP**。

IP 是個人資料，而這兩位使用者平常在同一個地方上班，看到的會是同一串數字，實際幫助有限。「裝置類型＋最後使用時間」已經足以回答這個功能真正要回答的問題：**我是不是在別人的電腦上忘記登出了。**

user agent 在**登入時**取得（`handleLogin` 從請求標頭讀出後傳給 `createSession`），存原始字串並截斷至 300 字元。顯示時才在**前端**折算成「Chrome on Windows」這種描述——那是顯示邏輯，規則會隨瀏覽器改版而變，放前端改起來不必動資料。

### 端點

| 端點 | 行為 |
|---|---|
| `GET /api/auth/sessions` | 回自己的 session 清單，標出哪一個是當下這台 |
| `DELETE /api/auth/sessions` | 登出**其他**所有裝置，保留當下這一個 |

只回自己的：`WHERE user_id = ?` 綁的是 session 帶出來的 user，沒有任何參數可以指定別人。

`DELETE` 沿用既有的 `destroyOtherSessions(env, userId, keepToken)`，不新增機制。

### `last_seen_at` 的寫入節流

每個請求都寫一次 `last_seen_at`，等於每個人每次操作都多一次 D1 寫入。

因此**超過一小時才更新一次**：顯示「2 小時前」這種精度本來就不需要秒級準確。判斷與寫入合併成單句帶條件的 UPDATE，不是「先讀再比對再寫」——理由同〈樂觀鎖必須是單句 SQL〉。

## 錯誤處理

- 裝置清單讀取失敗：該區塊顯示錯誤訊息，**不影響分頁其他區塊**。與 admin.html 的備份區、操作記錄區同一個模式。
- 「登出其他裝置」失敗：顯示錯誤並保持按鈕可用；成功後重新載入清單。
- 401（session 過期）：一律走既有的 `sessionExpired()`，導向 `/login`。不可靜默降級成單機模式。
- 單機模式（偵測不到 `/api/*`）：雲端區塊隱藏，不發任何請求，不留 console 錯誤。

## 測試

| 測什麼 | 怎麼測 |
|---|---|
| 裝置清單只回自己的 | 兩個帳號各有 session，確認甲看不到乙的 |
| 登出其他裝置不會登出自己 | 三個 session，執行後只剩當下這一個 |
| `last_seen_at` 一小時內不重複寫 | 連續兩次請求，確認只寫一次 |
| 升級前的舊 session（欄位為 NULL） | 不能讓清單整個壞掉，顯示為「未知裝置」 |
| 搬移後功能沒壞 | `tools/smoke.mjs`（零 pageerror、零 console.error） |
| 單機模式的分頁 | 瀏覽器實測：雲端區塊隱藏、無 console 錯誤 |
| 頂層函式沒被遮蔽 | `tests/shadow.test.mjs`（這一批新增前端函式，這道檢查會跑到） |

新測試一律用突變驗證真的抓得到 bug，至少涵蓋：拿掉 `user_id` 條件（變成看得到別人的裝置）、讓「登出其他」把自己也登出、拿掉節流（每次都寫）。

## 最大的風險

**搬動 4776 行檔案裡的 HTML，最可能的失敗是某個元素被搬走但程式仍在找它**——`getElementById` 回 `null`，然後整段 render 丟例外、畫面少一塊，而其他檢查都是綠的。

這正是 `tools/smoke.mjs` 存在的理由（它是為了兩次一模一樣形狀的事故而寫的）。搬移完成後必須跑它，四種情境都要綠。

## 實作順序

分兩個 commit，因為兩者的風險性質不同：

1. **後端 + migration**（裝置清單的端點與欄位）。純新增，不動既有路徑。
2. **前端分頁與搬移**。風險集中在這一步，跑完整的瀏覽器驗證。

## 附錄：為什麼不做 Google 日曆連動

使用者問過「能否讓使用者登入 Google 帳號後與 Google 日曆連動」。查證後的結論是**現階段不做**，理由記在這裡，避免日後重查。

**現況已有單向訂閱**：`/ics/:token` 提供 ICS feed，可加進 Google 日曆。缺點是 Google 抓取不積極，更新延遲可能達數小時到一天。

**要做到「即時同步」必須用 Google Calendar API + OAuth**，而那條路的門檻是：

- 「Testing」發布狀態 + External 使用者類型 → **refresh token 7 天後失效**，等於每週要重新授權一次，對自動同步是致命的。
- Google Workspace 組織的「Internal」應用程式不受這個限制——但兩位使用者的帳號都是 `@gmail.com`，**不是 Workspace 組織**，這條路走不了。
- 轉為「Production」則日曆權限屬於**敏感範圍**，必須通過 OAuth 驗證：示範影片、Search Console 網域驗證、**在網站上發布隱私權政策**、等待數週審核。範圍更大的權限還需要每年的第三方資安稽核。

**額外的安全代價**：授權後要保管使用者的 refresh token，那等同於對方整個 Google 日曆的存取權。本專案在這件事上一向保守——連每日備份都刻意不含密碼雜湊——存這種憑證是往反方向走一大步。

**還有一條專案自身的限制**：occurrence 引擎只存在前端（`CLAUDE.md` 明文禁止在 Worker 重新實作，理由是兩套必然分歧，而「提醒寄錯日期比沒有提醒更糟」）。因此即使要往 Google 寫事件，也**必須沿用 ICS／逾期提醒的模式**：前端展開 → 推上伺服器 → Worker 只負責送出。

**結論**：先把現成的 ICS 訂閱在「我的帳號」頁寫清楚、放明顯，實際用一段時間。如果「延遲數小時」可以接受，就停在這裡；若確實造成困擾，再回頭評估——屆時付出的代價會是為了一個已經被證實的問題，而不是一個猜測。

- <https://support.google.com/cloud/answer/15549945>（Testing 狀態的 7 天與 100 人限制）
- <https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification>（敏感範圍的驗證要求）
- <https://support.google.com/cloud/answer/13464321>（驗證要求總覽）
