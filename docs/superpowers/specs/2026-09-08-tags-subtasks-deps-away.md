# 標籤、子清單、前置作業、不在

日期：2026-09-08
狀態：**標籤與子清單已實作；前置作業與「不在」待確認**

## 這四件事是從哪裡來的

不是照抄 Asana。是拿 Asana 的資源清單（61 個群組）去對照**實際使用者的資料**，找出「她已經在用土法煉鋼的方式做的事」——土法煉鋼是需求的化石。

實際使用者有 45 個不重複的項目名稱，其中：

| 觀察到的化石 | 對應的缺口 |
|---|---|
| 名稱裡自帶分類關鍵字：管制藥品 ×5、PVF ×4、標案 ×3、網購／特賣 ×4 | **標籤**（一個項目只能有一個大項目，所以分類被寫進名字） |
| 「管制藥品申報 → 跟催報表 → 覆核報表 → 覆核 → 歸檔(覆核)」五個獨立項目，明顯是一條流程 | **前置作業** |
| 括號裡塞人名：`Q4藝文活動討論(小杜)`、`教特賣打單(瑞玲)` | 標籤也能吸收（不是指派，是「跟誰有關」） |
| `休假`、`下午休假` 被當成待辦項目 | **不在**（那不是一件要做的事） |

Asana 其餘 50 個資源群組（Portfolios、Goals、Budgets、Rates、SCIM、Timesheet approvals…）是給數千人的組織用的，這個系統有兩位使用者，照抄只會做出沒有人看得懂的東西。

## 四件事共用同一個既有抽象

**它們全部都能掛在 occKey 上，或完全不必碰 occKey。** 這不是巧合，是挑選的標準——會逼著我們改寫 occurrence 引擎的功能一律不列入。

| 功能 | 存在哪裡 | 碰 occKey 嗎 |
|---|---|---|
| 標籤 | `item.tags` | 否，整個項目共用 |
| 子清單 | `item.subtasks`（範本）＋ `item.subDone[occKey]`（勾選） | **是**，與 `doneMap` 同一個模式 |
| 前置作業 | `item.dependsOn` | 否（配對規則見下） |
| 不在 | `awayDates`（頂層，同 `customHolidays`） | 否 |

---

## 一、標籤

```js
item.tags = ['管制藥品', '月報']    // 字串陣列，正規化後去重、排序
```

### 為什麼是字串，不是像大項目那樣的實體

`majorProjects` 有 `{id, name}`，因為它要能改名而不讓底下的項目失去歸屬。標籤不需要——改名的需求低，而字串讓雲端合併直接沿用既有的 `tmMergeSets()`（新增看得到就留、單邊刪除才生效），不必為它發明新的合併規則。

**代價要說清楚**：打錯字會靜靜長出一個新標籤（「管制藥品」與「管制藥品 」是兩個）。緩解是輸入時列出既有標籤讓她點選，而不是每次重打。這是取捨，不是純好處。

### 為什麼不做 Asana 的 custom fields

custom fields 要先定義欄位（型別、選項、預設值、套用到哪些專案），才能開始用。她要的只是「這一組是管制藥品」——中間那一層定義工作是純粹的成本。等真的需要「數值型欄位」再說。

### 篩選的語意

與現有的類型篩選同一排，行為刻意一致：**同一個維度內是 OR，跨維度是 AND**。選「管制藥品」+「PVF」= 兩者皆顯示；再加選類型「作業」= 兩個標籤其中之一 **且** 是作業。

## 二、子清單

```js
item.subtasks = [{ id, text }]              // 步驟「範本」，整個項目共用
item.subDone  = { [occKey]: { [subId]: 1 } } // 勾選狀態，每一次各自獨立
```

### 為什麼範本共用、勾選各自

「管制藥品申報」每個月都要跑同一套步驟。步驟本身不會每個月變，但**這個月勾到哪裡**與上個月無關。

這正是 occurrence 引擎既有的分工：`item.recurrence` 是規則、`item.doneMap[occKey]` 是那一次的狀態。子清單只是把同一個模式再用一次，沒有引入新概念。

### 因此頻率變更時必須一起清掉

`btnConfirmItem` 在偵測到頻率變更時會清空 `done` / `doneMap` / `overrides` / `skipped`——**`subDone` 必須加進那一段**。CLAUDE.md 已經警告過這件事：occKey 的格式跟頻率綁定，漏改會留下孤兒資料，症狀是「改回原頻率時舊紀錄整批復活」。

### 主項目與子項目**不自動連動**

- 勾完所有子項 → **不會**自動把主項目標成完成
- 把主項目標成完成 → **不會**自動勾完所有子項

自動連動看起來貼心，但它會讓「我只是想記錄其中一步做完了」變成「整件事被標成完成」。那是靜默寫入錯誤資料，而排程系統的價值就建立在那些狀態是對的。

### 顯示：列上只給數字，展開才看細項

看板列上顯示 `☑ 2/5`，點開才展開細項。剛做完的效能優化（1461 列從 1292ms 降到 68ms）不能立刻被子清單吃掉——每個項目多五列，列數就多五倍。

## 三、前置作業（待確認）

```js
item.dependsOn = ['<item id>', ...]
```

### 純資訊，不自動移動任何日期

這是整段設計最重要的一條。

「A 延後了，B 自動跟著延後」聽起來是這個功能的重點，但它做的事是**在使用者沒看的時候改掉一個日期**。而這個專案已經寫過同一個判斷（WebMCP 那份文件裡）：

> AI 把日期改錯一天 → 你**永遠不會發現**，畫面看起來完全正常，只是那個日期默默地不對了。

自動順延與 AI 改日期是同一種失敗模式，差別只在誰動的手。所以：**前置作業只顯示狀態，不動資料。**

### 循環項目怎麼配對

不要求兩邊頻率相同（那條管制藥品的鏈可能月／週混用）。規則是：

> B 的某一次，配對到 A 在 **B 這一次的日期或之前**最近的那一次。

找不到就視為沒有前置（例如 B 的第一次早於 A 的第一次）。這個規則不需要 occKey 對得上，也不需要兩邊頻率一致。

### 不阻擋，只提示

A 還沒完成時勾 B，仍然勾得下去，但跳一個 toast：「管制藥品申報（8/31）還沒完成」。理由同〈刪除一律走 `deleteWithUndo()`〉：攔截式對話框擋不住「按太快」，而事後看得到才擋得住。

### 必須擋環

`A → B → A` 會讓顯示邏輯無限遞迴。設定時就要偵測並拒絕。

## 四、不在（待確認）

```js
awayDates = ['2026-09-15', '2026-09-16', ...]   // 頂層，形狀同 customHolidays
```

### 它影響什麼、不影響什麼

| 影響 | 不影響 |
|---|---|
| 日曆上標示出來 | **不移動任何項目的日期** |
| 落在「不在」期間的項目不算逾期（提醒信與指標卡都是） | 不改變循環規則 |

### 為什麼不順延

假日順延是**事前規則**——使用者在 modal 裡明確選過 `holidayRule`，而且國定假日是全年已知的。「不在」是**事後才知道的事實**（臨時請假），拿它去回頭移動日期，會讓歷史紀錄變成假的：那件事本來就是排在那天，只是人不在。

### 為什麼不做成一種項目類型

她現在就是那樣做的（`休假` 是一個 `meeting` 類型的項目）。代價是「休假」出現在待辦清單裡等著被打勾——**那不是一件要做的事**，混在裡面會稀釋清單的意義。

## 資料模型的收尾（四項共同）

新增欄位一律要同時更新這幾個地方，漏一個就是靜默的資料遺失：

- `snapshot()` / `applySnapshot()`——本機與雲端共用的序列化格式
- `normalizeItems()`——補齊與過濾，缺欄位的舊存檔不能讓 render 掛掉
- `threeWayMerge()`——`tmMergeList` 以 stableStringify 比對，**欄位集不一致會把「沒改過」誤判成「兩邊都改過」**，所以正規化必須產生 canonical 形狀
- `seed()`——示範資料要示範得到新功能，否則第一次開的人不知道有這些東西
- `buildReminderDigest()` / `buildICS()`——如果新欄位會影響提醒或訂閱的內容

## 實作順序

**先做標籤與子清單。** 兩者都只是「多存一個欄位」，不改變任何既有語意，風險低。

**前置作業與「不在」等這份文件確認後再動。** 兩者都改變「逾期」與「完成」的意義——而那正是這個系統唯一不能出錯的地方。
