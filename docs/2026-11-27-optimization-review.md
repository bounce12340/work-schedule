# 系統可以優化的地方（2026-11-27 盤點）

這份是盤點，不是已經決定要做的清單。每一項都寫了「為什麼」與「代價」，要做哪一項由使用者決定；
做的時候照往例：先寫驗收清單、再動工、驗收完才合併。

**最重要的一句話：功能已經比使用量多很多。** 接下來最划算的不是再加功能，而是讓已經做好的東西被找到、被用到，
以及讓每天打開的那幾個畫面更快、更順。

## 第一優先：讓做好的東西被用到

### 1. 問清楚為什麼三個人都把逾期提醒關了
提醒是預設開的，現在三個都是關的。可能是「全部都不要了」那顆按鈕、可能是信太多、也可能是內容沒用。
**原因不同，修法完全相反**（太多→改成每週一封；沒用→改內容；按錯→改按鈕）。先問人，不要猜。
- 代價：零程式。問完才知道要不要動。

### 2. 第一次登入的導覽（三步就好）
分享、行事曆訂閱、公開連結都是 0。〈「我的帳號」分頁〉那一節已經寫過：「沒有人找得到的功能等於不存在」。
做法：第一次登入時三張小卡——「新增第一件事」「把日曆接到手機」「把專案分享給同事」，可以略過，看過就不再出現
（記在 localStorage，同 `agentCapsSeen`）。
- 代價：小。要守住〈視覺基調〉：不跳全螢幕、不擋操作。

### 3. 衝突預覽接上畫面
〈衝突預覽〉引擎已經寫好也有測試（`tests/conflict.test.mjs`），但**還沒接上畫面**。
新增或改會議時，如果跟另一場撞時間，在 modal 裡多一行提示（不擋存檔）。
- 代價：小～中。引擎是純函式，只差畫面那一段與 smoke 斷言。

## 第二優先：每天打開的那一刻更快

### 4. `index.html` 太大了
現在 13,309 行、815KB（gzip 後約 260KB），每次開都要整個下載與解析。最大的幾塊：

| 區塊 | 大小 |
|---|---:|
| CSS 與靜態骨架 | ~170KB |
| agent 工作區（含 3B） | ~70KB |
| 語言字典 | ~47KB |
| 夥伴（小院子＋畫皮） | ~68KB |

兩條路，**都要使用者決定**：
- **甲（不違反零相依）**：把只有少數人用的區塊（agent 工作區、訂閱、夥伴的 SVG 畫皮）搬到同源的獨立檔案，用到才載入。
  代價：「單檔」這個前提要改寫成「單一入口、零第三方」；iOS app 打包時 `prepare-www.mjs` 要一起複製；測試抽原始碼的方式要跟著改。
- **乙（不動結構）**：只做量測與小修——拿掉沒用到的 CSS、壓縮 SVG 路徑。收益小，但風險也小。

### 5. service worker 的導覽改成「先給快取、背景更新」
CLAUDE.md〈響應速度〉已經列為「收益最大」：現在每次開都等網路，快取裡明明有完整的畫面。
- 代價：部署後要多開一次才看得到新版。可以配一條「有新版，點這裡更新」的提示把代價補回來。

### 6. 手機效能檢查放進 CI
`tools/check-mobile.mjs` 抓到過三個真實 bug，但不在 CI。可以只把「不橫向溢出」與「點擊目標大小」這兩條
（不隨環境浮動的）放進 `smoke` job，速度那一段照舊手動跑。
- 代價：CI 多一兩分鐘。

## 第三優先：補完已知的缺口

這些在 CLAUDE.md 或 PR 說明裡被標成「還沒做」或「沒驗」：

| 項目 | 現況 | 大小 |
|---|---|---|
| 刪帳號時一起取消 Paddle 網頁訂閱 | 沒做：刪了帳號，訂閱還在扣款 | 中（要打 Paddle API） |
| Paddle 退款自動收回 Pro | 沒做：要人去後台取消 | 小 |
| 英文模式下夥伴卡還有中文（「換夥伴」「半大」等） | 字典漏了幾句 | 小 |
| 關閉風險時可以寫一句說明 | 端點不收 body | 小（前後端各一點） |

| 上線後的實測：GitHub webhook `ping`、Gmail 的「取消訂閱」、版本歷史真的退回一次 | 都沒在真環境驗過 | 各十分鐘，使用者操作 |

## 第四優先：讓程式碼好維護

### 7. 主程式拆成幾個命名空間
CLAUDE.md〈尚未做的重構〉：`DateUtil`／`OccurrenceEngine`／`Store`／各畫面。**單獨一個 PR、不夾帶任何行為變更**，
測試靠區段註解定位，所以區段名稱不能動。

### 8. CLAUDE.md 本身太長
已經超過 2,200 行。新的人（或新的 agent）讀不完，就會漏掉關鍵的那一條。
做法：CLAUDE.md 只留「不能拿掉的規則」與索引，各功能的詳細理由搬到 `docs/areas/<功能>.md`。
- 代價：純文件，但要小心不要在搬的時候把規則弄丟——搬完逐條對照。

## 刻意不建議做的

- **再加新的大功能**：使用量的數字說得很清楚，先把現有的用起來。
- **網頁版推播（Web Push）**：要另一套金鑰與另一條 service worker 路徑；目前只有 1 台裝置在用推播。
- **改 occurrence 引擎**：它是全檔最好的設計，沒有壞就不要碰。

## 建議的順序

1. 問使用者提醒為什麼關掉（不寫程式）
2. 第三優先表格裡的「小」項目一次做完（英文漏字、Paddle 退款、放掉認領、風險說明）
3. 衝突預覽接上畫面
4. 第一次登入的導覽
5. 決定 `index.html` 走甲或乙、service worker 要不要改
