# 按一次「取消訂閱」，把自己鎖在系統外面

**日期**：2026-09-17
**症狀**：helen 登不進去。按「變更密碼」要舊密碼（想不起來）；按「忘記密碼」畫面說已寄出，信永遠不來。
**狀態**：已用破窗鎚救回（直接改 D1 並登出所有裝置）。**根因未解**：她的地址仍在拒收名單上。

## 經過

- **08-24** 逾期提醒信寄給她，正常送達。
- 某個時間點，她（或 Gmail 的介面）按下了信件上的**「取消訂閱」**。
- **09-09** 逾期提醒信被 AgentMail 以 403 擋下。當時只留了一行 `console.warn`，沒有人看到。
- **09-17 16:16** 她在另一台裝置嘗試登入，密碼想不起來（那台原本登著的裝置從 09-09 起就沒再輸入過密碼）。
- **16:28** 她按「忘記密碼」。伺服器**做完了每一件該做的事**：驗 Turnstile、產生一次性連結、寫進 `password_resets`、呼叫 `sendMail`。畫面回「已寄出」。
- 信沒有寄出去。查 AgentMail 那個信箱的寄件記錄，16:28 前後**一封都沒有**。
- 從另一個寄件信箱送一封測試信，當場被退：

```
Message rejected: Recipient(s) blocked: helen3569@gmail.com
(suppressed by AgentMail: Unsubscribed via List-Unsubscribe)
… suppression entries are read-only and the DELETE endpoint rejects them
```

## 根因：三件事疊在一起

單獨看每一件都是對的決定，疊起來才變成死路。

| # | 決定 | 當初的理由 | 這次的角色 |
|---|---|---|---|
| 1 | `ADMIN_EMAILS` 名單內的帳號，**管理者不能重設密碼** | 防另一位管理者橫向接管 | 關掉了第一條路 |
| 2 | 名單內的人**只能靠「忘記密碼」自救** | 收得到那個信箱的信＝證明是本人 | 把全部賭注押在 email 上 |
| 3 | **寄信商自己在每封信上掛 `List-Unsubscribe`** | 不是我們加的，`sendMail` 只送 to/subject/text/html | 按一次就把 email 這條路也關掉 |

第 2 條的前提是「email 一定到得了」。**那個前提在使用者按下取消訂閱的那一刻過期**——而系統沒有任何地方察覺得到。

**這是這份文件裡第四次前提過期**（前三次：「系統沒有寄信基礎設施」、「Mac runner 貴」、「開發者沒有 Mac」）。前三次都是前提變寬、可以做更多事；**這一次是前提變窄，而且是使用者自己一個動作造成的**。

## 兩個更糟的細節

**一、那顆按鈕不是關掉一種信，是封鎖一個地址。** 系統裡本來就有三顆「我不想收」的開關（逾期信、小植物的信、推播），使用者關掉任何一顆都不影響其他管道。而寄信商加的那一顆**凌駕在全部之上**，而且使用者按的時候完全不知道自己順便關掉了密碼重設。

**二、整條失敗鏈是隱形的。**

| 關卡 | 當時 | 它其實在看什麼 |
|---|---|---|
| `/api/auth/forgot` 回應 | 200「已寄出」 | 刻意不區分成敗（防帳號列舉） |
| `password_resets` 有一列 | ✓ | 連結產生了，與寄信無關 |
| `console.error` | 有寫 | 在 Cloudflare 後台，沒有人會去翻 |
| `/admin` | 一片正常 | **根本沒有「寄信有沒有成功」這一格** |

唯一看得到真相的地方是 AgentMail 的寄件記錄——而那在系統外面。

## 這次怎麼救的

`tools/reset-password.mjs` 那把破窗鎚就是為這種情況存在的。這次走的是等價的路：產生密碼 → 用 `src/crypto.js` 同一套 PBKDF2 算出雜湊（並反向自驗一次）→ 單句 UPDATE（確認 `changes === 1`）→ 清掉她所有 session、待用連結與失敗計數 → **補一筆 `admin_activity`**。

最後那一步不能省：繞過 Worker 的操作預設不留痕跡，而「是誰改的」正是這種記錄要回答的問題。

## 要修的（依序）

1. **`/admin` 要看得見寄信失敗。** 目前沒有任何一格在回答「信到底有沒有寄出去」。同〈看得見的備份才是備份〉——這是同一個道理第四次出現。
2. **交易信與訂閱信要分家。** 密碼重設、註冊驗證碼是**交易信**，使用者不該有辦法把它們退訂掉；逾期提醒、植物的信才是訂閱信。目前兩者共用同一個 AgentMail 帳號，而**拒收名單是帳號層級的**——換寄件信箱沒有用（已實測）。要真的分家得用兩個獨立的寄信帳號或第二家供應商。
3. **不要把帳號救援全部押在單一管道上。** 名單內的帳號目前只有 email 一條路。至少要在文件裡把破窗鎚寫成正式的救援程序，並確保「碰得到資料庫的人」永遠不只一個。

## 學到的

1. **「使用者自己按的」也會讓前提過期。** 前三次前提過期都是外部條件變化（接上寄信服務、確認計費、買了 Mac），這一次是**使用者在別的介面上按了一個我們看不到的按鈕**。設計「唯一的救援管道」時，要問的不只是「這條路現在通嗎」，而是「**誰有辦法把它關掉，而我們會不會知道**」。
2. **兩道各自正確的保險，疊起來可能是一扇鎖死的門。** `ADMIN_EMAILS` 擋管理者、email 是唯一自救路——各自都對，交集是空的。加第二道保險之前要先問：**它與既有那道的交集，還剩下路嗎？**
3. **供應商會在你的信上加東西。** `sendMail` 只送四個欄位，`List-Unsubscribe` 是 AgentMail 加的。**「我們沒寫」不等於「它不在」**——同〈原始碼這一側驗不到簽好的 app 身上有什麼〉。
